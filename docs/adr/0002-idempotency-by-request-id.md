# ADR-0002. Идемпотентность по requestId

**Статус:** принято

## Контекст

Повторы, тайм-ауты и повторная отправка клиентом не должны создавать дубликаты бронирований
и повторно менять доступность номера.

## Решение

- Клиент может передать `requestId` в `POST /api/booking`; иначе он генерируется. Поле уникально
  в `bookings` — повторный запрос возвращает уже созданное бронирование, а гонка двух параллельных
  вставок разрешается уникальным индексом.
- Тот же `requestId` передаётся в Hotel Service. `room_reservations.request_id` уникален:
  повторный `confirm` возвращает существующую блокировку без повторного `times_booked++`,
  повторный `release` ничего не меняет.
- `release`, пришедший до `confirm` (тайм-аут на стороне клиента), сохраняет маркер `RELEASED`,
  и запоздавший `confirm` с тем же `requestId` отклоняется с 409.

## Последствия

Повторы Resilience4j безопасны для `confirm` и `release`. Один `requestId` нельзя переиспользовать
для другого бронирования.
